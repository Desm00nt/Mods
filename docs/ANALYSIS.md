# Spraute Engine Lite 1.9.5 — как устроен мод и что в нём не так

Документ описывает мод по декомпилированным исходникам (`spraute_engine-src/`). Все цифры и выводы ниже
проверены на коде или запуском классов мода (инструменты — в `tools/analysis/`).

## 1. Что это за мод

**Spraute Engine** — «движок сюжетов» для Minecraft **Forge 1.20.1**: внутри игры есть полноценная IDE,
в которой пишут сюжеты (квесты, диалоги, катсцены, NPC, интерфейсы) на собственном языке или собирают их из блоков,
а затем загружают в мир и запускают.

| | |
|---|---|
| mod id / название | `spraute_engine` / Spraute Engine **Lite** 1.9.5 |
| автор / лицензия | R3ad1x (t.me/spraute) / All Rights Reserved |
| зависимости | Forge `[47,)`, Minecraft `[1.20.1,1.21)` |
| объём | 422 класса верхнего уровня (1211 `.class`), ≈142,5 тыс. строк Java после декомпиляции |
| язык сюжетов | 38 ключевых слов, 411 команд, 210 функций, 116 событий — см. [`LANGUAGE_REFERENCE.md`](LANGUAGE_REFERENCE.md) |
| миксины | 35 (19 общих, 16 клиентских) |
| сеть | 68 типов пакетов: 20 клиент→сервер, 47 сервер→клиент, 1 в обе стороны |
| сторонние библиотеки | нет (GeckoLib не нужен — свой рендер моделей); JavaScript — через Nashorn, который поставляется с Forge |

## 2. Архитектура

```
ForgeMod (@Mod)                       platform/forge — единственное место, где есть код Forge
  ├─ Platform.install(ForgePlatform)  platform/      — свои абстракции: Hooks/ClientHooks (шина событий
  ├─ SprauteEngine.init()                               с приоритетами и отменой), Platform, PacketChannel
  │    ├─ Modules.common()      → ~20 серверных подсистем подписываются на Hooks
  │    ├─ ClientModules.client()→ ~35 клиентских (только если клиент)
  │    └─ Addons.load()         → аддоны = другие моды с манифестом Spraute
  └─ ForgeEvents / ForgeClientEvents  → переводят события Forge в Hooks
```

Мод написан **платформонезависимо**: весь Forge изолирован в `platform/forge` (11 классов), остальной код видит только
свои интерфейсы. Порт на NeoForge/Fabric свёлся бы к новой реализации `platform/`.

Жизненный цикл сервера (`SprauteEngine`): при `SERVER_ABOUT_TO_START` сканируются модели, грузятся настройки движка и
загруженные сюжеты, открывается `ScriptEnvironment`; каждую тику — шаг сюжетов, раздача контента клиентам,
события `servertick`/`playertick`; при остановке выгружается ~25 подсистем.

### 2.1. Сюжеты: от текста до действия в мире

```
 .svs (блоки) ──BlockCodegen──┐
                              ▼
 .sst (текст) ──Lexer──► токены ──Parser──► AST (lang/Ast) ──Analyzer──► ошибки/предупреждения, подсказки IDE
                                                │
 «Загрузить в игру» (пакет Deploy, нужен оператор) ──► SprauteRuntime.deploy(): анализ, проверка id,
                                                │      сохранение в мир (world/spraute/<id>.sst)
 /script start <id>, autostart ──► ScriptEnvironment создаёт SprauteScriptInstance
                                                │
                                   Emitter (5,5 тыс. строк) компилирует AST в цепочку действий
                                   ScriptPerformer(Builder) — по команде на шаг
                                                │
                       ScriptEnvironment.tick() каждую серверную тику продвигает все сюжеты;
                       выражения считает Eval (динамические типы: число=double, строка, список, да/нет)
```

* **Надёжность**: каждый сюжет тикается в своём `try/catch (Throwable)` — сломанный сюжет останавливается и пишет
  ошибку в консоль редактора, сервер не падает. Перебор идёт по копии списка, так что сюжеты могут запускать и
  останавливать друг друга без `ConcurrentModificationException`.
* **Состояние** работающих сюжетов (переменные, позиции, чекпоинты) сохраняется в `world/spraute/running.dat`.
* **Режимы**: обычный сюжет — один на всех (`player` — тот, кто запустил); `solo` — своя копия у каждого игрока;
  `autostart [once]` — запуск при входе игрока; `general` — «общий» сюжет, работающий в самой игре (меню, миры).
* **События** (`on <событие> { … }`) приходят из `GameEvents`, куда их транслируют подписки на Forge-события.
* **JavaScript/Java** (`runtime/JsEngine`, `JavaBridge`): по умолчанию песочница без доступа к классам Java;
  `/sprautejs unsafe on` (уровень прав 4) открывает доступ, флаг хранится файлом `world/spraute/js_unsafe`.

### 2.2. Редактор (клиент)

`/editor` открывает `SprauteScreen` — IDE на собственном UI-тулките (`ui/`: окна, вкладки, деревья, редактор кода
с подсветкой, автодополнением и поиском). Внутри: проводник проекта, текстовые и блочные сюжеты, дизайнер интерфейсов,
катсцены (таймлайн + запись), камера, ассеты (модели, текстуры, звуки, сущности), пиксельный редактор текстур,
квесты, магазины, зоны и пути (с редакторами прямо в мире), рецепты, настройки движка, справка, консоль, «Проблемы».

* Проекты лежат в `<папка игры>/spraute/projects/<имя>/` (папки `scripts/`, `blocks/`, интерфейсы, модели…).
* При загрузке в мир файлы проекта синхронизируются с сервером (`content/ProjectContent`): сравнение по хэшам,
  белый список папок и расширений, лимит 32 МБ на файл, защита от `../` в путях.
* Проект можно экспортировать в отдельный мод (`ExportDialog` → `ModExport`, Forge или Fabric): такой мод несёт
  файлы проекта внутри jar, а Spraute Engine при открытии мира сам загружает их (`export/BundledProjects`).
* **Кастомные предметы, блоки и мобы регистрируются при запуске игры из `spraute/projects/*`**
  (`CustomItems.register()`). Следствие: для игры по сети у клиента и сервера должны быть **одинаковые** проекты,
  иначе Forge не пустит на сервер из-за несовпадения реестров.

### 2.3. Мир, сущности, отображение

* **NPC** — `AnimatedEntity` (`spraute:npc`) со своим форматом моделей (geo-JSON в стиле Bedrock + анимации,
  `core/parser`, `core/model`), рендер `SpGeoRenderer`; модели из проектов — `SprauteModelEntity`.
  Позы костей считаются на клиенте и отправляются на сервер (`PartPoseSync`) — для хитбоксов и привязок к костям.
* **Камера и катсцены** — `CameraDirector` (клиент), `CameraState` (сервер), профили камер, клипы `ClipSim`.
* **Интерфейсы** — документы `GuiDoc`/`GuiSchema`, рендер `GuiView`, HUD-оверлеи, панели, привязанные к сущностям.
* Подсистемы: квесты и журнал, магазины и монеты, зоны, пути и навигация, эффекты частиц (`Casts`, `FxEngine`),
  рецепты, правила игрока (что ему можно: ломать, бегать, открывать инвентарь…) — через миксины `Rules*`.
* Только в полной версии (код есть, команды закрыты): бой и боссы, прокачка, стелс, постройки/структуры, пост-эффекты.

### 2.4. Сеть и права

Один канал `SimpleChannel`. Большие пакеты (сюжет, контент, настройки) режутся на части по 30 000 байт.

* Пакеты редактора (`Deploy`, `Undeploy`, `RunCommand`, `SourcesSet`, `EngineSet`, `DebugSet`, `ContentOffer`…)
  проходят через `SprauteRuntime.canEdit()`: оператор с уровнем прав **≥ 2** или владелец одиночного/LAN-мира.
* Игровые пакеты (ответ на выбор, клик по интерфейсу, клавиши, сделка в магазине, слежение за квестом, позы костей…)
  доступны всем игрокам.

### 2.5. Миксины

19 общих: правила игрока (инвентарь, предметы, опыт, езда, режим игры, ломание блоков), хитбоксы, перехват рецептов,
данные блоков, аксессоры `FireBlock`/`SpawnPlacements`. 16 клиентских: камера, блокировка мыши, пост-эффекты,
анимации и скины игрока, экраны контейнеров, скрытие сплэша и блоков, модели предметов.
Все **63 цели** из refmap существуют в 1.20.1 (`tools/analysis/check_mixin_targets.py`) — при `defaultRequire: 1`
это важно: промах любой инъекции уронил бы игру при запуске.

### 2.6. Lite против Full

`Edition.LITE = true`. Ограничения сделаны «мягко» — реализация есть в jar, закрыт только доступ:

* 42 команды языка (раздел «Бой и боссы» целиком, `skills …`, `stealth …`, `build …`, `post …`, `loot …`, `cast`,
  `aoe`, `mob spawn`, `dungeon place`, события навыков и `mobspawn`): `Analyzer` выдаёт ошибку
  «Есть только в полной версии Spraute Engine», `Emitter` отказывается их собирать, в блочном редакторе они скрыты.
* В редакторе: редактор мира, панель модов, файлы эффектов/пост-эффектов/структур/боя/стелса/прокачки;
  скрипты клипов в катсценах пропускаются; MCP-сервер для ИИ-ассистентов — заглушка.

## 3. Найденные проблемы

Каждая проблема подтверждена на коде; №1–2 — ещё и запуском классов **оригинального** jar.
Исправления — отдельным коммитом поверх точной декомпиляции, у каждого в коде есть комментарий `Fix`.

| № | Где | Суть | Последствие | Статус |
|---|---|---|---|---|
| 1 | `editor/project/ScriptTemplates`, `lang/Analyzer`, `lang/ParamType` | Демо-проект («Пример») использует `emotion HAPPY_NEW`, а такой эмоции в 1.9.5 нет (есть 24: NEUTRAL, ANGER, JOY…). Подсказки тоже предлагали несуществующие `HAPPY_NEW, SAD1, ANGRY` | Свежесозданный пример сразу показывает ошибку «Неизвестная эмоция» и **не загружается в мир** | ✅ исправлено |
| 2 | `editor/visual/BlockTypes` | Скрытие Full-блоков: для событий использован префикс `ev:` вместо `on:` | В палитре Lite видны 4 блока событий (`skilllearn`, `skilllevel`, `skilluse`, `mobspawn`), которые дают ошибку при использовании | ✅ исправлено |
| 3 | `editor/ClientEvents` | `/editor mcp on` в Lite: сервер — заглушка | Игрок включает MCP и видит «выключен — /editor mcp on» без объяснения | ✅ исправлено |
| 4 | `net/SprauteNetwork.runCommand` | Консоль редактора доступна с уровня прав 2, но выполняла команды с уровнем **4** | Модератор (уровень 2) мог выполнить `/op`, `/stop` или `/sprautejs unsafe on` → Java в сюжетах → произвольный код на сервере | ✅ исправлено (свой уровень игрока; владелец одиночного мира — по-прежнему 4) |
| 5 | `SprauteEngine.onServerTick` | Наличие обработчиков `servertick`/`playertick` пересчитывается раз в 100 тиков | После запуска мира или загрузки сюжета эти события не приходят до 5 секунд | не исправлено (мелочь): считать флаг сразу после `deploy` |
| 6 | `net/SprauteNetwork.BIG` | Буферы недокачанных больших пакетов не удаляются | Утечка памяти, если клиент оборвал передачу (только у операторов) | не исправлено (мелочь) |
| 7 | пакет `PartPoses` | Любой игрок может задать позы костей моделей в радиусе 96 блоков; длина массива не проверяется | Подмена хитбоксов модифицированным клиентом; кривой пакет — исключение в логе сервера | не исправлено (особенность дизайна) |
| 8 | реестры (`CustomItems.register`) | Кастомный контент регистрируется из локальной папки проектов | Разные проекты у клиента и сервера → отказ во входе | особенность дизайна (см. 2.2) |
| 9 | `editor/project/Project.importModel` | `noneMatch(m -> m.dir().equals(o))` сравнивает папку модели с путём файла — всегда `true` | Безвредно: дубли отсекает следующая проверка | не исправлено |
| 10 | `data/storytelling/dimension_type/white.json` | Чужое пространство имён, нигде не используется | Безвредный «хвост» другого проекта | не исправлено |
| 11 | `runtime/Images.slug` | `toLowerCase()` без `Locale` | На турецкой локали `I` → `ı`, папки контента могут не совпасть | не исправлено (мелочь) |
| 12 | `runtime/JsEngine` | Нужен Nashorn (`org.openjdk.nashorn`) | Forge 1.20.1 поставляет его для coremods, так что обычно работает; если нет — JS-команды падают с ошибкой в консоли сюжета (сервер не падает) | риск, не ошибка |

Что проверено и **не** является проблемой:

* **Выделенный сервер**: все общие классы мода загружаются JVM с выкинутыми клиентскими классами Minecraft
  (`tools/analysis/LoadTest.java`); 14 классов, которые там не грузятся, используются только из клиентского кода под
  проверками `isClient()` / `FMLEnvironment.dist` / ленивыми лямбдами.
* Права на пакеты редактора проверяются; загрузка контента защищена от `../`; имена проектов санитизируются.
* Встроенные примеры из справки мода проходят его же анализатор (кроме ожидаемых случаев: Full-команды и команды
  «общих» сюжетов).

## 4. Насколько исходники соответствуют jar

| Проверка | Результат |
|---|---|
| Компиляция (ECJ, Java 17, против заглушек Minecraft/Forge) | **0 ошибок**, 1181 класс |
| Структура: поля и методы каждого класса против оригинала (`compare_members.py`) | совпадают; 3 объяснимых отличия (добавленный `reloadWelcome()` и ABI анонимных классов у ECJ) |
| Статическое состояние: каждый класс инициализирован в обеих сборках, все статические поля сравнены (`StaticDiff`) | **0 отличий** (после исправления 3 ошибок Vineflower, см. ниже) |
| Поведение языка: Lexer/Parser/Analyzer/Eval на 832 сюжетах (по 2 на каждую команду, все конструкции, ошибочный ввод) и 60 выражениях (`DiffTest`) | **байт-в-байт** одинаковый дамп (7,6 МБ) |
| Блочный редактор: генерация кода для 529 типов блоков (`BlockTest`) | одинаково |
| Цели миксинов | 63 из 63 существуют в 1.20.1 |

**Ошибки декомпиляции, найденные этими проверками.** Vineflower 1.11.2 переносит `static final X = f(Y)` из конца
статического блока в объявление поля — даже если `static {}` заполняет `Y` позже (воспроизведено на примере из
10 строк). Так получились пустые `Emotions.NAMES` (все эмоции считались неизвестными), `BlockDef.SHAPES`
и `QuestGoals.EVENTS`. Исправлено, в коде оставлены комментарии `decompile note`.

Другие ручные правки декомпиляции: восстановление `Eval.binary()` (операторы) и части `SstLanguage`/`FxTextures` по
FernFlower; типы событий у лямбд `addListener` взяты из байткода (без них Forge подписал бы лямбду на *все* события);
5 конструкций `try/finally` с «семафорами» Vineflower свёрнуты обратно; переименования переменных, сломанных
декомпилятором.

**Что не проверено**: настоящая сборка Gradle и запуск в игре — из песочницы нет доступа к maven.minecraftforge.net.
Версия Forge в `gradle.properties` (47.3.0) выбрана как совместимая с `[47,)`; точная версия, которой собирали
оригинал, в jar не записана.

## 5. Как пользоваться исходниками

См. [`spraute_engine-src/README.md`](../spraute_engine-src/README.md): сборка `gradlew build`, запуск `gradlew runClient`.
История в git разделена так, чтобы её было удобно сравнивать:

1. `f5dafad` — сырая декомпиляция + проект Gradle + инструменты;
2. `5661a05` — ручные правки до компиляции без ошибок;
3. `389b1e1` — исправление ошибок Vineflower (точная копия поведения оригинала);
4. следующий коммит — исправления ошибок самого мода (раздел 3).
